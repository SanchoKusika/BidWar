# BidWar

Telegram Mini App: платный и бесплатный топы проектов. Позиция в платном топе
покупается (Raise) и отбирается (Attack), в бесплатном — зарабатывается
голосами за задания.

Спецификация лежит **вне репозитория**, в Obsidian (`Проекты/BidWar`): механики,
схема данных, платежи, план разработки. Перед задачей смотреть туда, а не
восстанавливать требования по коду. Что из спеки уже написано, а что ещё нет —
в документе `12 Состояние реализации`.

## Состояние

Приложение выложено: **app.bidwar.world**.

Работает: витрины Paid и Free с категориями и курсорной пагинацией, вход через
Telegram, добавление проекта в Free Top с OG-превью, счётчик кликов, правила и
документные страницы, платёжный слой на моке, платный вход, **Raise (свой и
чужой) и Attack**, лента событий, суточный борд, стрелки изменения позиции и
ставки, профиль с настоящими тратами.

С 10.09.2026 работает и бесплатная половина: **задания и голоса** (срез 1.7).
Три типа заданий — заход в проект (возобновляется раз в сутки), приглашение
друга (награда за каждого, после его первого выполненного задания) и подписка
на канал (`getChatMember`, требует бота-администратора). Голоса отдаются любому
проекту бесплатного топа, своему или чужому, и двигают его позицию. У Free-топа
появились свои лента событий и разрез «Today» — по голосам.

Настройки в профиле сведены с мобильным китом (10.09.2026): вибрация стала
настоящей — отклик приходит по факту события, а не по нажатию, — «история
платежей» ведёт к чекам ниже на том же экране, у правовых страниц появилась
редакция. Строки кита, которых в продукте не будет, удалены, а не спрятаны:
«подтверждать каждый платёж», «выйти», «удалить аккаунт».

Не проверено на живых данных: `subscribe` — ни один канал в базе пока не имеет
бота администратором.

> **Платежи идут через мок** — рубеж держит `PAYMENT_PROVIDER=mock` в окружении
> Edge Functions (сервер, обязателен, дефолта нет — незаданная переменная
> роняет функцию, а не молча подставляет мок), `PREVIEW.mockPayments` только
> красит список способов оплаты в интерфейсе поверх него. Подтверждение
> мгновенное и без реального провайдера. **Чек-лист боевого запуска начинается
> с `PAYMENT_PROVIDER`** — это единственная переменная в проекте, которая
> стоит денег, а не рисует заглушку; снимается вместе с флагом и реальным
> провайдером в 1.10.

Вёрстка перенесена вся, и с закрытием 1.7 за ней стоят настоящие данные:

- блоки без источника данных спрятаны за флагами в `src/shared/config/preview.ts` —
  по этому файлу видно границу между витриной и работающей функцией; после 1.7
  там осталось четыре флага, и невёрстанных механик в Этапе 1 нет;
- **все шесть шторок подключены** — последней `VoteSheet` (10.09.2026).
  `RaiseSheet` обслуживает и свою ставку, и донат в чужую, `AttackSheet` считает
  предпросмотр по числам сервера;
- экран проекта достижим и с витрины, и из профиля.

Тесты — двумя уровнями, см. «Команды» ниже.

## Стек

React 19 + TypeScript + Vite, FSD-структура, CSS-модули на дизайн-токенах.
Бэкенд — Supabase: PostgreSQL, Edge Functions (Deno), Realtime. Node 22.

## Команды

```bash
npm run dev            # локальный фронт
npm run build          # прод-сборка
npm run check          # типы + линт + prettier + правило изоляции платформы + тесты
npm run format         # prettier --write
npm run test           # тесты Edge Functions (deno test), требует установленного Deno; входит в check и CI
npm run test:db        # интеграционные тесты хранимок против живой базы (deno test),
                        # нужны Deno и SUPABASE_DB_URL в .env; в check и CI НЕ входят
npm run functions:deploy  # выложить все Edge Functions разом (в CI их нет)
```

`npm run check` намеренно совпадает по составу с CI. Если добавляешь проверку в
пайплайн — добавь и сюда: расхождение всплывает только после пуша, уже красным.

### База

```bash
npm run db:reset       # накатить миграции с нуля на локальный стек (нужен Docker)
npm run db:push        # применить миграции на связанный проект
npm run db:diff        # чем схема связанного проекта отличается от миграций
npm run db:types       # перегенерировать src/shared/api/database.types.ts
npm run db:seed:dev    # заменить строки-заглушки в топах настоящими проектами (только стенд)
```

`db:types` запускать после каждой миграции — файл генерируемый, руками не
править, prettier его не форматирует.

Связать локальный репозиторий с проектом:

```bash
npx supabase login
npx supabase link --project-ref <ref>
```

В `supabase/migrations/` кроме схемы лежат хранимки и вьюхи: идентичность
(`resolve_telegram_identity`), дедупликация кликов (`register_project_click`),
применение платежа одной транзакцией (`apply_payment`, идемпотентна, внутри неё
же живёт Attack), начисление и трата голосов (`apply_task_completion` и
`cast_votes` — единственные места, где голоса появляются и исчезают), права
бота в канале (`apply_channel_admin`) и шесть вьюх для чтения — агрегаты
категорий (`category_stats`), две ленты событий (`stake_activity`,
`vote_activity`), два суточных борда (`paid_today_top`, `free_today_top`) и
изменения за сутки (`paid_movement_24h`). Часть логики
опущена в базу намеренно — там, где несколько связанных записей обязаны быть
одной транзакцией, и там, где читать надо мимо RLS, не отдавая наружу лишних
колонок: `stake_activity` не показывает автора события, потому что публично
известно, по кому ударили, а не кто ударил.

Позиция и её изменение нигде не хранятся: и текущая, и суточной давности
считаются из ставок, вторая — реконструкцией по леджеру
(`paid_movement_24h`). Снапшотов и cron под это нет.

> Локальные файлы миграций и история в связанной базе (`bidwar-dev`) были
> разъехавшимися: часть миграций применялась через Supabase MCP с генерируемым
> таймстемпом. **Сведено 10.09.2026** двумя `supabase migration repair` —
> `db push` работает. Причина, а не симптом: миграции применяли через MCP.
> Так больше не делать, только `db push`, иначе журнал разъедется снова.

### Edge Functions

```text
health           версия и живость
auth             initData → users.id
bot              вебхук Telegram, /start с реферальным параметром
add-project      создание записи + OG-фетч с защитой от SSRF
click            счётчик переходов с дедупликацией
create-payment   валидация и создание платежа (сейчас — мок)
payment-webhook  применяет платёж через apply_payment; пока не вызывается
                 никем — ждёт вебхука настоящего провайдера (срез 1.10)
attack-quote     пол цели, коэффициент зачисления и остаток лимитов для шторки
my-spending      свои платежи и чеки (у payment_transactions нет политики на
                 чтение, а auth.uid() у мини-аппа не существует)
remove-my-projects  только для разработки (PAYMENT_PROVIDER=mock): обнуляет аккаунт,
                 удаляя свои проекты, платежи, ставки и голоса
tasks            список заданий с состоянием под аккаунт и баланс голосов
cast-votes       отдать голоса проекту бесплатного топа
verify-channel   владелец проверяет, стал ли бот админом его канала
check-subscription  подписчик проверяет подписку, задание засчитывается
notify           разбирает очередь уведомлений и шлёт их ботом; вызывается не
                 человеком, а расписанием базы (см. ниже)
```

#### Уведомления: что завести один раз

Очередь наполняют триггеры в базе, а разбирает `notify`. Между ними стоит
расписание `pg_cron`, которое раз в минуту дёргает функцию через `pg_net`. Чтобы
оно заработало, нужны три вещи, и ни одна не ставится миграцией — секретам не
место в файле, который лежит в репозитории:

```bash
# 1. Секрет отправщика — в окружении функции
npx supabase secrets set NOTIFY_SECRET=<секрет> --project-ref <ref>
```

```sql
-- 2. Он же и адрес функции — в Vault, откуда их читает drain_notifications()
select vault.create_secret('<секрет>', 'notify_secret');
select vault.create_secret('https://<ref>.supabase.co/functions/v1/notify', 'notify_url');
```

```bash
# 3. Сама функция
npx supabase functions deploy notify --project-ref <ref>
```

Пока секретов в Vault нет, задание тихо ничего не делает: это лучше, чем
падение раз в минуту — журнал, полный ожидаемых ошибок, перестают читать.
Проверить, что расписание живо: `select * from cron.job_run_details order by
start_time desc limit 5`.

**Деплой ручной, автоматизации нет** — в CI функции не выкладываются:

```bash
npm run functions:deploy                  # все разом
npx supabase functions deploy <name>      # одну
npx supabase secrets set BOT_TOKEN=... WEBHOOK_SECRET=...
```

`verify_jwt` каждой функции задан в `supabase/config.toml`, а не флагом в
команде: массовый деплой без этого включит проверку JWT `bot` и
`payment-webhook` — двум вебхукам, которых зовут вообще без заголовка
`Authorization`. Выкладывать лучше все разом: разъехавшийся деплой уже стоил
среза — в проде висела `create-payment` от 1.5, и любая атака отвечала ошибкой
валидации, хотя код в `main` был верный.

Общая обвязка (разбор запроса, единый формат ошибки, логирование) — в
`supabase/functions/_shared/`. ESLint функции не проверяет: у Deno свои импорты.

## Деплой

Фронт живёт на Cloudflare Pages, выкладывает его GitHub Actions
(`.github/workflows/deploy.yml`): пуш в `main` — продакшн, любая другая ветка —
превью-окружение. Сборка идёт в CI, потому что `VITE_*` вшиваются в бандл на
этапе сборки, а не читаются в рантайме.

Что нужно завести один раз:

| Где                 | Что                      | Значение                                  |
| ------------------- | ------------------------ | ----------------------------------------- |
| Actions → Secrets   | `CLOUDFLARE_API_TOKEN`   | токен с правом `Cloudflare Pages: Edit`   |
| Actions → Secrets   | `CLOUDFLARE_ACCOUNT_ID`  | ID аккаунта Cloudflare                    |
| Actions → Variables | `VITE_SUPABASE_URL`      | URL проекта Supabase                      |
| Actions → Variables | `VITE_SUPABASE_ANON_KEY` | публикуемый ключ, он и так уходит в бандл |

Без секретов Cloudflare шаг деплоя пропускается, а не валит проверки на pull
request. Без переменных `VITE_*` сборка падает намеренно: молча выложенное
приложение без бэкенда хуже упавшего деплоя.

Вручную, с локальной машины:

```bash
npx wrangler login
npm run build
npx wrangler pages deploy dist --project-name bidwar
```

### Адреса

Одно развёртывание доступно по трём именам — это нормально и так и задумано:

```text
bidwar.world          сайт (Этап 2), индексируется
app.bidwar.world      мини-апп, этот адрес идёт в BotFather
bidwar.pages.dev      служебный алиас Pages, плюс превью веток
```

Кастомный домен в Pages **не заменяет** `*.pages.dev`: адрес выдаётся проекту
навсегда, и на нём же живут превью веток (`<branch>.bidwar.pages.dev`). Убрать
его нельзя.

Поэтому индексируется только `bidwar.world`, а мини-апп и все `*.pages.dev`
отдают `X-Robots-Tag: noindex` — правила по хостам в `public/_headers`. Именно
заголовком, а не `Disallow` в `robots.txt`: тот запрещает обход, но не
индексацию, и закрытый им адрес всё равно может всплыть в выдаче. Заголовок
краулер увидит, только если пустить его на страницу.

`public/_headers` задаёт ещё CSP и кеширование. Там намеренно **нет**
`X-Frame-Options` и есть `frame-ancestors` с доменами Telegram: Mini App
открывается внутри айфрейма, и запрет фрейминга её сломает.

## Правила, которые проверяет CI

- **Прямых обращений к `window.Telegram` вне `shared/platform` и `app/telegram` нет** —
  `scripts/check-platform-isolation.sh`. Всё, что знает про Telegram, живёт за
  интерфейсом `platform/`, иначе веб-версия в Этапе 2 пишется заново.
- **Нижние слои не импортируют из `app/` и `widgets/`** — `no-restricted-imports`
  в `eslint.config.js` для `entities`, `features`, `shared` и `pages/*/model`.
  Логика, утёкшая в композицию, — это и есть тот веб, который придётся дописывать.
- Типы, линт, prettier и сборка проходят.

## Переменные окружения

`.env.example` — список. Во фронт попадает только `VITE_*`; `SUPABASE_SERVICE_ROLE_KEY`,
`BOT_TOKEN` и ключи провайдеров живут в окружении Edge Functions и в бандл не
попадают никогда.
