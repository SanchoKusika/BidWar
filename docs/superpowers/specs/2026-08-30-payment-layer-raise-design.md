# Срез 1.5 — платёжный слой на моке и Raise

Дизайн, согласованный 30.08.2026. Требования — в Obsidian: `08 План разработки`,
`01 Механики`, `03 Данные`, `04 Платежи и валюты`, `12 Состояние реализации`.

Срез снимает главное ограничение продукта: **денег в нём нет ни одной строкой**.
После него появляются платёжный слой, платный вход, Raise и первые записи в
леджере. Вместе с ними — тестовый раннер, которого в проекте тоже нет.

---

## Границы среза

**Входит:** интерфейс `PaymentProvider` и его мок; конвертация в очки с
фиксацией `original_amount` и `fx_rate_used`; идемпотентность; транзакция
применения эффекта; платный вход (открывающий Raise) и Raise-довзнос; подключение
шторок Raise → Pay → Result; раннер `deno test` и первые тесты.

**Не входит:** Attack (1.6), задания и голоса (1.7), история операций и чеки в
профиле (1.8), настоящий провайдер (1.10). Флаг `receipts` остаётся включённой
заглушкой: записи в `payment_transactions` появятся, но экран истории их ещё не
читает.

---

## Решения, принятые до кода

Пять развилок, закрытых на этапе дизайна, — вместе с причиной, чтобы к ним не
возвращаться.

### 1. Проект на время оплаты живёт в статусе `pending_payment`

Платный вход — это открывающий Raise-платёж, и до подтверждения строки в топе
быть не должно. Заводить её после оплаты нельзя: `payment_transactions.project_id`
объявлен `not null`, то есть id проекта нужен уже в момент создания платежа.

Поэтому строка создаётся сразу, но со статусом вне `active`. Это дёшево ровно
потому, что весь остальной код уже фильтрует по `status = 'active'`: RLS-политика
`projects_read_active`, оба индекса витрин, оба уникальных индекса
(`projects_one_active_per_user_and_type_idx`, `..._per_url_and_type_idx`) и вьюха
`category_stats`. Строка в `pending_payment` для них не существует.

Отвергнутая альтернатива — сделать `project_id` nullable и держать данные
будущего проекта в самом платеже. Чище по смыслу («не заплатил — записи нет»), но
разводит два пути `create-payment` (довзнос на существующий проект против входа с
нуля) сильнее, чем они расходятся по существу.

### 2. Функции называются по действию: `create-payment` и `payment-webhook`

В `02 Архитектура` они помечены как `payments` и `actions`, но существующие пять
функций названы глаголом (`add-project`, `click`), и ломать это ради схемы не
стоит. Документ поправить тем же заходом.

### 3. Мок подтверждает платёж синхронно, внутри `create-payment`

`openInvoice` работает только внутри настоящего Telegram и только с реальным
`provider_token`, которого до 1.10 не будет. Поэтому `MockPaymentProvider` не
отдаёт ссылку на оплату: он применяет эффект прямо в вызове и возвращает исход.

Фронт из-за этого не получает ветку «а это мок»: он смотрит на поле `status` в
ответе и либо показывает результат, либо открывает оплату.

Отказ, дубль вебхука и зависший `pending` мок умеет выдавать по команде
(`mockCommand` в теле запроса) — это нужно тестам, а не интерфейсу:

- `decline` — провайдер отказал, очки не начисляются;
- `stuck_pending` — платёж создан, но подтверждение не приходит вовсе;
- `duplicate` — применение вызывается дважды подряд, как при повторном вебхуке;
  второй вызов обязан оказаться no-op.

### 4. Раннер — `deno test`, без второго раннера под фронт

Всё, что обязано быть покрыто тестами (`08 План разработки`), — серверное:
идемпотентность, floor, хейркат, конвертация валют. Оно живёт в Edge Functions на
Deno. Заводить рядом Vitest ради фронта, где проверяемых бизнес-правил пока нет,
преждевременно.

`npm run test` → `deno test supabase/functions` и добавляется в `npm run check`.
Состав `check` обязан совпадать с CI, поэтому шаг заводится и в пайплайне — там
понадобится ещё и установка самого Deno (`denoland/setup-deno`), которой в
workflow сейчас нет.

### 5. Мок доступен из интерфейса, но честно подписан и закрыт флагом

Между 1.5 и 1.10 приложение публично, а мок подтверждает оплату бесплатно — то
есть платное #1 можно занять даром. Это принято сознательно: в топе сейчас только
сидовые проекты, а срез, который нельзя потрогать в телефоне, проверить нечем.

Условия: в `PaySheet` мок показывается **отдельным способом оплаты с явным
названием тестового**, имена GlobalPay и Platega к нему не подставляются
(`shared/content/payments.ts` описывает реальных провайдеров и до 1.10 не
используется); весь путь закрыт флагом в `shared/config/preview.ts`.

**Флаг обязан быть снят до боевого запуска.** Это единственное место в проекте,
где включённый флаг стоит денег, а не рисует заглушку.

## Данные

Схема из `03 Данные` заведена первой миграцией целиком: `payment_transactions` и
`stake_transactions` существуют с самого начала и просто пусты. Новая миграция
минимальна.

```sql
-- projects.status получает четвёртое значение
alter table projects drop constraint projects_status_check;
alter table projects add constraint projects_status_check
  check (status in ('active', 'pending_payment', 'hidden', 'blocked'));

-- payment_transactions.provider получает мок
alter table payment_transactions drop constraint payment_transactions_provider_check;
alter table payment_transactions add constraint payment_transactions_provider_check
  check (provider in ('mock', 'globalpay', 'platega', 'paddle', 'telegram_stars'));
```

Индексы, RLS и `app_config` не трогаются. Лимиты (`paid_limits`) и курсы
(`fx_rates`) засеяны и используются как есть; новых ключей срез не заводит.

### Брошенные оплаты

Уникальные индексы ограничивают только `active`, поэтому пользователь может
накопить несколько строк в `pending_payment`, бросая оплату. Удалять их нельзя:
на них ссылается `payment_transactions.project_id`.

Правило: `create-payment` **переиспользует** существующую строку
`pending_payment` того же пользователя и типа, обновляя ссылку, категорию и OG.
Мусор ограничен одной строкой на пользователя на топ.

### Гонка за адрес

`projects_one_active_per_url_and_type_idx` не резервирует адрес за строкой в
`pending_payment`, поэтому двое могут одновременно оплачивать вход с одним URL.
Проигравший упрётся в `23505` уже в момент подтверждения, когда деньги списаны.

`create-payment` проверяет занятость заранее (дёшево), а транзакция применения
ловит `23505` и переводит платёж в `failed`, не начисляя очков. Для мока этого
достаточно. Для настоящего провайдера это случай возврата — отдельная задача
среза 1.10.

## Платёжный слой

`supabase/functions/_shared/payments/`:

- **`types.ts`** — интерфейс из `04 Платежи и валюты` без изменений, `id`
  расширен значением `'mock'`. `mode: 'telegram_native' | 'hosted'` предусмотрен
  сразу, как того требуют обязательства перед вебом.
- **`mock.ts`** — `MockPaymentProvider`. `toPoints`/`fromPoints` тождественны
  (валюта `UZS`, курс из `app_config.fx_rates`, якорь 1 очко = 1 UZS).
  `createPayment` применяет эффект и возвращает исход. `mockCommand` переключает
  сценарий: `decline`, `stuck_pending`, `duplicate`.
- **`apply.ts`** — тонкая обёртка над хранимкой `apply_payment` (ниже).
- **`registry.ts`** — выбор провайдера по `PAYMENT_PROVIDER` из окружения
  функции; неизвестное значение — ошибка при старте, а не молчаливый мок.
  Переменную добавить в `.env.example` вместе с остальными серверными.

## Транзакция применения эффекта

Единственное место, которое двигает деньги и очки. Живёт **в базе**, а не в
функции: `supabase-js` не умеет многооператорных транзакций, а здесь обязательны
`FOR UPDATE` и атомарность (`02 Архитектура`). Это тот же приём, что уже применён
для `resolve_telegram_identity` и `register_project_click`.

```sql
create function apply_payment(
  p_payment_id        uuid,
  p_provider_event_id text,
  p_confirmed         boolean
) returns table (applied boolean, project_id bigint, points_granted bigint)
security definer
```

Порядок внутри одной транзакции:

1. `select ... from payment_transactions where id = p_payment_id for update`.
2. Если `status <> 'pending'` — вернуть `applied = false` и выйти. **Это и есть
   идемпотентность:** повторный вебхук с тем же событием ничего не меняет.
   Второй рубеж — `unique (provider, provider_event_id)` на случай гонки.
3. Если `p_confirmed = false` — `status = 'failed'`, выйти.
4. Заблокировать строки `projects` **по возрастанию `id`**: свой проект и
   текущего лидера топа, если это другая строка. Порядок обязателен — на нём
   держится отсутствие дедлока во встречных операциях (в Attack это станет
   критично, и правило вводится сразу).
5. `paid_amount += points_granted`;
   `initial_stake = coalesce(initial_stake, points_granted)` — база для floor
   будущих атак фиксируется первым платежом;
   `status = 'active'`, если строка была в `pending_payment`.
6. `insert into stake_transactions (type='raise', amount=+points, payment_id,
transaction_group_id)`.
7. `payment_transactions`: `status='confirmed'`, `confirmed_at=now()`,
   `provider_event_id`.
8. Пересчёт `rank1_since`: если проект стал лидером своего топа — проставить
   `now()`, у прежнего лидера снять. Лидер категории здесь не участвует, его
   считает на лету вьюха `category_stats`.

Инвариант, который держит вся конструкция: **сумма очков проекта равна сумме его
stake-транзакций** (сверочный запрос №1 из `03 Данные`).

## Edge Functions

### `create-payment`

Принимает `initData`, `intent: 'raise'` и либо `projectId` (довзнос), либо
`categoryId` + `url` (открывающий вход).

Валидация до создания платежа:

- `initData` через существующий `verifyInitData`;
- сумма не ниже `min_paid_amount` из `app_config.paid_limits` — на сервере, а не
  по числу из клиента;
- для довзноса: проект существует, принадлежит вызывающему, `type = 'paid'`,
  `status = 'active'`;
- для входа: слот платного топа свободен, адрес не занят, OG-фетч через
  существующий `_shared/og.ts` с той же защитой от SSRF.

Дальше: создать или переиспользовать строку `pending_payment`, записать
`payment_transactions(status='pending')`, позвать `provider.createPayment`.

Ответ единый для всех провайдеров:

```ts
{ paymentId, status: 'confirmed' | 'pending' | 'failed', openUrl?, projectId, pointsGranted }
```

### `payment-webhook`

Точка входа настоящих провайдеров: `parseWebhook` (проверка подписи до разбора
тела) → `apply_payment`. В 1.5 её не зовёт никто, кроме тестов, но она пишется и
покрывается сейчас — иначе 1.10 начнёт с написания нового кода применения
эффекта, то есть второго места, где двигаются деньги.

## Клиент

Новая фича `features/raise` — вызов `create-payment` и типы ответа. Правила floor
и лимитов в клиент не переезжают: он читает `fetchPaidLimits` **только для
предпросмотра**.

Точки входа, обе на вкладке Paid:

- `OwnPositionPanel` → «Занять это место» / Raise → `RaiseSheet` → `PaySheet` →
  `ResultSheet`;
- `AddProjectSheet` — сегмент Paid перестаёт быть заблокированным, ведёт в
  `PaySheet` с открывающей ставкой.

По `status` из ответа: `confirmed` → `ResultSheet` с новой позицией; `failed` →
сообщение об отказе; `pending` → шторка ожидания (у мока не встречается, кроме
команды `stuck_pending`).

После успеха витрина и своя позиция перечитываются — как это уже делает
`refreshAfterCreate` в `pages/free/ui/Mobile.tsx`.

## Тесты

Раннер ставится этим же срезом. Обязательный минимум — там, где ошибка стоит
денег:

- **идемпотентность:** один `provider_event_id` применяется однократно; повторный
  вызов `apply_payment` — no-op;
- **конвертация:** `original_amount` не пересчитывается никогда, `fx_rate_used`
  записан, очки посчитаны по курсу из конфига;
- **минимум ставки:** платёж ниже `min_paid_amount` отвергается до создания
  инвойса;
- **открывающий вход:** `pending_payment` → `active` только при подтверждении;
  при отказе строка остаётся неактивной, очки не начислены;
- **`initial_stake`** фиксируется первым платежом и не меняется вторым;
- **`rank1_since`** при смене лидера Paid-топа: проставляется новому, снимается у
  прежнего;
- **`initData`:** валидный, подделанный, просроченный.

Хейркат и floor из общего списка `08 План разработки` относятся к Attack и
ставятся срезом 1.6 — здесь для них ещё нет кода.
